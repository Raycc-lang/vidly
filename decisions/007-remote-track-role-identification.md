# 007 — Remote Track Role Identification: media-state + onFirstPacketReceived

**Status:** Accepted (2026-07-10, commit e4a492d)
**Code:** `NativeWebRtcClient.assignRemoteVideoTrack`, `reclassifyRemoteVideoTracks`, `onRemoteVideoFirstPacket`, `attachChatChannel` (media-state handling)

## Problem

A peer can send up to two video tracks — camera and screen share — and the receiver must render them in different places (camera in the small PiP tile, screen in the main view). So the receiver has to answer: *which incoming track is which?*

Two obvious answers don't work:

1. **Track ids.** The sender names its tracks (`vidly-video`, `vidly-screen`), but in **Unified Plan the receiver-side track id is regenerated by the receiver** and bears no relation to the sender's id (W3C decision, w3c/webrtc-pc#1718). Ids cannot classify.
2. **Track liveness.** A muted track is not a dead track. When the remote turns its camera off, it keeps the `RtpSender` (so on→off→on needs no renegotiation) — the receiver's cached camera track stays `LIVE`, it just stops producing frames. Android WebRTC exposes **no track-muted event** (browsers get `track.onmute`/`onunmute`; Android doesn't). So "is this receiver LIVE?" cannot distinguish an active screen track from a stale muted camera track.

The concrete failure: remote shares screen with camera off. One track arrives; `onTrack` fires before the remote's role announcement, so arrival-order binding guesses "camera" — and the screen renders in the tiny PiP tile forever.

## Decision

Three cooperating signals, mirroring the web client:

1. **Arrival order** is only a provisional default: `assignRemoteVideoTrack` slots incoming tracks into camera/screen roles using the remote's last-known live flags as a hint, first-track-to-camera otherwise.
2. **`media-state` messages** over the chat DataChannel (booleans `cam`/`screen`, sent on every toggle and on channel open) are the **authoritative role announcement**. When one arrives, `reclassifyRemoteVideoTracks` moves a mis-bound track to its correct role.
3. **`RtpReceiver.Observer.onFirstPacketReceived` is the authoritative "alive" signal.** It fires only when RTP packets actually flow for that receiver, and it is what gates reclassification: we record the firing track as `activeVideoTrack`, and a track may only be *moved* between roles if it is the one actually producing packets. Without this gate, a camera-on→off→screen-share sequence would mis-bind the stale (LIVE but muted) camera receiver to the screen role. `onFirstPacketReceived` also serves as the Android substitute for `track.onunmute`: on camera off→on, no new track arrives and `onTrack` does not re-fire (same RtpSender), so this callback is the only reliable "frames are flowing again" trigger to re-attach the renderer.

A role going false in media-state clears `activeVideoTrack` if it pointed at that role's track, so a later reclassify never promotes a muted receiver.

## Alternatives considered

- **MSID / stream-id plumbing in SDP.** Both tracks are deliberately sent in the same stream (`vidly-native`); per-track MSIDs would need custom SDP munging — fragile across libwebrtc versions.
- **Renegotiate a fresh track on every camera toggle.** Would make `onTrack` a usable signal, but costs an SDP round trip per toggle and broke the web client (receiver kept pointing at the disposed track).

## Trade-offs and failure modes

- When *both* roles are live but the tracks got swapped, we cannot disambiguate (no usable ids) and keep arrival-order binding — same accepted limitation as the web client.
- Role correctness depends on the chat DataChannel being open; until it is, provisional binding may be wrong for a few hundred ms.

## Revisit if

- libwebrtc Android ever exposes mute/unmute events or receiver-visible sender track ids — either would let reclassification drop the `activeVideoTrack` heuristic.
